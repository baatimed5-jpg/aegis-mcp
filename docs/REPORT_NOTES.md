# Notes for writing the PFE report

Use these notes as the skeleton of the written report. Every number must come from
`evaluation/REPORT.md` (generated from the CSV files in `evaluation/results/`): cite the table, never
retype a number from memory. Design reasons are in `docs/DECISIONS.md` (D1-D38): quote the D-number.

## 1. Suggested chapter plan
1. **Introduction**: LLM agents now call tools through MCP. Two problems: (a) security: tool results
   and descriptions are untrusted text that can carry *indirect prompt injections*; (b) cost: tool
   results are large JSON documents, most of their fields are useless for the question, and every token
   is paid and fills the context window. Contribution: a gateway that solves both, with two ML parts.
2. **Background / state of the art**: MCP (servers, tools, Streamable HTTP, stdio, `_meta`); prompt
   injection (direct vs indirect, tool poisoning, ASCII smuggling); existing defences (keyword filters,
   classifiers such as fine-tuned DeBERTa, LLM-as-judge); context compression (summarization, pruning,
   caching). Position AegisMCP: a protocol-level proxy, transparent to agents and servers.
3. **Requirements and architecture**: functional (aggregation, namespacing, policies, approvals, PII,
   injection scan, optimization, audit, dashboard) and non-functional (latency overhead, fail-closed,
   reproducibility). Diagrams: `docs/ARCHITECTURE.md` (component, sequence, data model).
4. **Gateway design**: middleware pipeline with two ordered lists (D1) and why an "onion" design could not
   run the order experiment; deny = exception, audit always runs (D2); fail-closed audit (D19).
5. **Contribution A: injection detection**: dataset construction (public + synthetic financial,
   template-level split, leakage check = 0, D27/DATASETS.md); 4 detectors; calibration (D34); results
   table (REPORT.md "Injection detectors"); attack evaluation incl. the adaptive attacker (REPORT.md
   "Attacks and false positives").
6. **Contribution B: context optimization**: rule pruning, compact tables, evidence recovery (why it
   makes pruning safe), cache at the downstream boundary (D3); learned pruning (labels, features,
   task-level split, recall-first threshold, D35); results (REPORT.md "Token savings" and "Learned vs rule").
7. **Evaluation**: benchmark (50 generated tasks, answers computed from the data, auto checks + judge),
   configurations, metrics with formulas (spec §8), live results (task success) + offline replay (tokens),
   the order experiment (filter→compress vs compress→filter).
8. **Dashboard and deployment**: Angular screens (screenshots), REST/WebSocket API (D37), Docker compose.
9. **Limits and future work** (section 4 below), **Conclusion**.

## 2. Key messages to defend
- **Transparent**: agents and servers are unchanged; the gateway speaks MCP on both sides.
- **Defence in depth**: auth + allow lists + human approval stop damage even when a detector misses
  an injection (the transfer still needs approval).
- **Safe compression**: pruning never destroys information thanks to evidence recovery; the learned
  pruner falls back to rules when the question is missing.
- **Honest evaluation**: answers computed from the data, test sets never used for tuning, template-level
  split, adaptive attacker, every number regenerated by a script, failures reported.

## 3. Likely jury questions (short answers)
- *Why not only an LLM detector?* Latency and cost per call, and it can itself be prompt-injected;
  see the latency column of the detector table. The combined detector is cheap and robust.
- *Why DeBERTa-v3-small?* Strong on short-text classification, small enough for CPU inference.
- *Is the synthetic data biased?* Yes, it follows our templates; that is why the test uses unseen
  templates and the public deepset test split, and results are reported per source.
- *How do you know pruning does not hurt answers?* Live task success with vs without optimizer, field
  recall of the learned pruner on unseen questions, and evidence recovery as a safety net.
- *Why replay offline?* Tool results are deterministic, so token savings are exact without an LLM;
  only task success needs the LLM (free-tier quota, D30).
- *Overhead?* REPORT.md gives p50/p95 added milliseconds per call per configuration.
- *Single point of failure?* Yes, like any gateway; it is stateless except approvals (in-memory futures,
  D7); scaling needs Redis pub/sub for approvals (future work).

## 4. Limitations (write them yourself, they show maturity)
- Free-tier LLM quota: number of live runs per configuration (see run counts in REPORT.md).
- One domain (wealth management, synthetic data), one assistant model.
- Injection labels of deepset are partly noisy; synthetic attacks come from our templates and one LLM.
- Number checker accepts the right number anywhere in the answer (D27).
- Learned pruning trained on 50 tasks only (small data, task-level split of 30/10/10).
- Approvals are in-memory (single gateway instance).
